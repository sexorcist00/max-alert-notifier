# iOS: план варианта с сервером и AlarmKit

Статус: **план, кода нет**. Документ описывает, что придётся построить, чего это стоит и где
неизвестность. Собрать iOS-приложение из среды разработки этого репозитория нельзя — нужен
Mac с Xcode, это не обходится.

---

## Почему нельзя повторить Android-схему

На Android приложение слушает чат двумя способами: читает уведомления МАКСа и держит своё
TLS-соединение. На iOS **оба** способа закрыты системой:

| Что делает Android-версия | Почему невозможно на iOS |
| --- | --- |
| `NotificationListenerService` — читает уведомления чужих приложений | API не существует ни с какими правами; ни сайдлоад, ни профиль разработчика этого не меняют |
| Держит сокет к `api.oneme.ru` в foreground-службе | Приложение уходит в suspend через секунды после сворачивания; сокет закрывается |
| Звонит через `STREAM_ALARM`, перебивая «Не беспокоить» | Требует entitlement Critical Alerts **или** AlarmKit (см. ниже) |

Вывод: узнать о сообщении iPhone сам не может. Единственный способ разбудить приложение в
фоне — **push с сервера**. Отсюда вся архитектура.

---

## Что изменилось: AlarmKit (iOS 26)

Apple открыла сторонним приложениям механизм системного будильника. Он даёт ровно то, что
нужно тревоге:

- звонит **сквозь беззвучный режим и режимы фокусирования**;
- полноэкранное окно со «Стоп» на экране блокировки, Dynamic Island, Apple Watch;
- **не требует одобрения Apple** — достаточно `NSAlarmKitUsageDescription` и разрешения
  пользователя при первом заведении будильника.

Это существенно проще, чем Critical Alerts, который Apple выдаёт по индивидуальному запросу.

**Ограничение, которое определяет всю схему:** AlarmKit звонит **в назначенное время**. Наш
триггер непредсказуем, значит будильник надо ставить «на сейчас» в момент прихода push.

## Архитектура

```
   ЧАТ MAX
      │
      ▼
┌──────────────────────────────┐
│ СЕРВЕР (VPS)                 │
│  • держит сессию MAX         │  ← сюда переезжает токен аккаунта
│  • ловит NOTIF_MESSAGE       │
│  • матчер уровней (красный / │
│    жёлтый / отбой)           │
│  • шлёт APNs                 │
└──────────────┬───────────────┘
               │ APNs, priority 10, alert-push
               ▼
┌──────────────────────────────┐
│ iPhone                       │
│  Notification Service Ext.   │  ← просыпается на каждый push (~30 с работы)
│      │                       │
│      ├─ красный → AlarmKit   │  → воет, пробивая беззвучный и фокус
│      └─ жёлтый  → обычное    │
│                   уведомление│
└──────────────────────────────┘
```

### Что переиспользуется

Сервер — это **уже написанный `termux/`-сторож** с заменённым «выходом»: вместо звука на
телефоне он отправляет APNs. Матчер уровней, слова отбоя, дочитывание истории после обрыва —
всё это уже есть и переносится почти без правок. Собственный протокол MAX разбирать заново не
нужно: он разобран и покрыт тестами в Android-версии, а PyMax работает как есть.

## Шаги

Каждый шаг проверяем отдельно; следующий не начинается, пока предыдущий не подтверждён.

| № | Шаг | Как проверить, что готово |
| --- | --- | --- |
| 1 | Поднять VPS, перенести `termux/`-сторож, вход в MAX по SMS **с российского IP** | В логе `match in chat …` при тестовом сообщении |
| 2 | Оформить Apple Developer Program ($99/год), выпустить APNs-ключ `.p8` | Ключ и Team ID на руках |
| 3 | Минимальное iOS-приложение: регистрация в APNs, отдаёт device token на сервер | Токен виден в базе сервера |
| 4 | Сервер шлёт тестовый push (priority 10, alert) | Уведомление приходит на заблокированный iPhone |
| 5 | Notification Service Extension: перехватывает push, читает уровень | В расширении логируется `red`/`yellow` |
| 6 | **Ключевой шаг:** расширение ставит AlarmKit-будильник «на сейчас» | Телефон воет при выключенном звуке и включённом «Не беспокоить» |
| 7 | Уровни: жёлтые — обычное уведомление, красный — будильник; отбой снимает будильник | Проверка всех трёх переходов |
| 8 | Живучесть: переподключение сервера к MAX, дочитывание истории, повтор push | Сообщение, отправленное при выключенном сервере, поднимает тревогу после старта |

## Чего это стоит

| Пункт | Цена |
| --- | --- |
| Apple Developer Program | **$99/год, обязательно** — push недоступен на бесплатном профиле |
| Mac с Xcode | обязателен, иначе приложение не собрать и не подписать |
| VPS | от ~$3/мес; **российский IP желателен** — MAX не выдаёт код авторизации на зарубежный адрес |
| Поддержка | протокол MAX неофициальный: ломается — чиним и на сервере, и в Android-версии |

## Риски и что делать

| Риск | Насколько вероятен | Запасной ход |
| --- | --- | --- |
| **AlarmKit не ставится из расширения уведомления** — сценарий известен, но в документации Apple не описан | средний, это главная неизвестность плана | Push с флагом `interruption-level: critical` (нужен entitlement Critical Alerts от Apple) либо `time-sensitive` — тише, но без сервера-посредника |
| Расширению не хватит ~30 с | низкий | Ставить будильник первым действием, всё остальное — после |
| APNs задерживает или дропает push | средний при `content-available` (silent push троттлится) | Слать **видимый** alert-push с priority 10 — он не троттлится |
| Токен MAX на сервере скомпрометирован | последствия тяжёлые | Отдельный VPS только под это, диск зашифрован, доступ по ключу, тексты сообщений не логируются, токен в файле `chmod 600` |
| MAX отзывает сессию сервера | средний | Уведомление «нужен повторный вход» на iPhone; повторный вход — только с российского IP |
| Apple меняет правила AlarmKit | низкий | Возврат к Critical Alerts |

## Что сильно дешевле и работает уже сегодня

Android-сторож **звонит на iPhone обычным телефонным звонком**. Входящий вызов пробивает
беззвучный и «Не беспокоить» штатными настройками iOS («Разрешить вызовы от» + «Повторные
вызовы»). Ни сервера, ни Mac, ни Apple Developer, ни iOS 26 — работает на любом iPhone.
Ограничение честное: нужен второй телефон на Android, который и так уже дежурит.

Если сервер не нужен ради самого сервера — этот путь закрывает ту же задачу за полчаса работы.
